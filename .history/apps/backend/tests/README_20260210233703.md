# Backend Test Guide (camp-clean-ddd-sample 방식)

이 문서는 `camp-clean-ddd-sample`의 테스트 철학(비즈니스 규칙 우선, GWT 스타일, 레이어 분리)에 맞춰 `clean-ddd/apps/backend`의 테스트를 운영하기 위한 기준입니다.

## 핵심 원칙

- 비즈니스 규칙(도메인/유스케이스) 회귀를 최우선으로 탐지합니다.
- 테스트는 `Given / When / Then`(GWT)으로 읽기 쉽게 작성합니다.
- 인프라(DB)는 **초기부터 허용**하되, 실행 속도/플레이키 관리를 위해 **fast vs db**로 분리합니다.

## 레이어(폴더) 규약

- `tests/units/**`: 순수 비즈니스 규칙(값객체/엔티티/도메인 서비스)
  - 금지: DB/네트워크/시간 의존(필요 시 주입/고정)
- `tests/scenarios/**`: 유스케이스 조합(핵심 흐름)
  - 허용: 모듈 경계의 포트(레포지토리/클라이언트)는 테스트 더블로 대체
  - 목적: “규칙이 이렇게 조합된다”를 빠르게 검증
- `tests/db/**`: DB 통합 테스트(MikroORM + 실제 Postgres)
  - 목적: 매퍼/스키마/레포지토리/쿼리의 정합성 검증
  - 원칙: 테스트는 `RUN_DB_TESTS=1`일 때만 동작
- `tests/*.e2e-spec.ts`: E2E(최소 개수)

## GWT 사용법

- `test-utils/gwt.template.spec.ts`의 `given/when/then`을 사용합니다.

## 실행 방법

- 빠른 테스트(기본):
  - `pnpm -C apps/backend test:fast`
- DB 통합 테스트(명시적 opt-in):
  - `pnpm -C apps/backend test:db` (필수: `TEST_DATABASE_URL` 환경변수 설정)
  - 로컬 Docker Postgres(기본값)로 실행: `pnpm -C apps/backend test:db:local`
- E2E:
  - `pnpm -C apps/backend test:e2e`

## DB 테스트 운영 가이드

- DB 테스트는 로컬/CI에서 동일한 URL을 쓰지 않도록 `TEST_DATABASE_URL`를 사용합니다.
- 테스트 데이터는 각 테스트 케이스마다 정리(삭제/초기화)하여 독립성을 보장합니다.
